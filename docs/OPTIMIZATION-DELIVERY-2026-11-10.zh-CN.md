# inbora 优化交付记录

本次按已批准的六批计划实现。应用版本仍为 0.3.5，主库及自动化扩展均保持版本 3；没有新增依赖、运行时、服务或账号配置步骤，没有为本批生成安装包。

## 实现范围

| 批次 | 已实现内容 | 验证重点 |
|---|---|---|
| 查询 | 完整事件行一次解码；同步只读事务内批量投影；仅当前20项加载预览；准确目标历史；资格回退先筛选；自动候选关联排除后惰性挑选 | 列表、排序、旧未知覆盖、最新补证持久顺序、人稿恢复、父子关系和目标隔离 |
| 索引 | 六个固定名称索引，核对列序、排序方向及校对规则 | 一致备份、私有副本试安装、完整性和外键、业务摘要不变、旧迁移可打开 |
| 刷新 | 150ms固定合并窗口、同类单在途及一次尾随、15秒状态兜底、focus补查 | 持续风暴仍显示进展；目标/选择/请求序号保护；旧状态不能覆盖新控制；未保存人稿保留 |
| 收取 | 正常响应单次读取/解析、固定错误分类、不可变共享摘要、请求与页面代际隔离、分阶段有界耗时 | 字符串原生ID、混排和晚到、重复页/未前进、隐藏旧列表、坏对象/持续增长会话公平续查 |
| 统计与提示词 | 鉴权只读 `getDiagnostics`；累计模型/状态、已知及未知用量、平均/P95、阻塞Top10、通道收取信息；简短具体指令及去重 | 不猜日期/通道/费用，不复制私人全局语料；20题边界、预算和敏感/注入防护 |
| 保留维护 | CLI与桌面共享引用保护、默认14天、空闲维护及24小时周期、每批最多100份、可取消和容量报告 | 有引用不删、未知/链接不删、改写及中断保留、计数与字节一致、无候选轮询不取消维护 |

## 性能测量方法

运行 `pnpm exec tsx scripts/benchmark-queries.ts --large`。使用本机 Node v26.13.0、同一套本地依赖、独立合成数据库；不访问真实网页，不调用真实模型，不发送消息。

稀疏样本沿用优化前每会话10条消息的形状。混合样本增加草稿、修订、意图、收据、正负补证、冲突和观察记录。每个规模先读一次，再运行20次，报告预热中位数与最近秩P95。SQL计数使用 SQLite `verbose` 实际执行追踪，包含 BEGIN/COMMIT，不使用 `prepare` 次数。计时本身也包含追踪开销。

最终数值与逐项结果保存在同目录的 `OPTIMIZATION-BENCHMARK-2026-11-10.json`，见其 `results`。优化前约733.47ms与247.10ms来自先前5次稀疏样本中位数；不能把混合样本或不同轮次的P95当作相同基线。

| 样本 | 收件箱中位数 / P95 | 状态中位数 / P95 | 当前目标详情中位数 / P95 |
|---|---:|---:|---:|
| 一万条稀疏 | 38.97 / 41.56ms | 0.29 / 0.35ms | 2.18 / 2.76ms |
| 一万条混合 | 62.68 / 64.54ms | 2.51 / 3.05ms | 2.22 / 2.66ms |
| 十万条稀疏 | 496.11 / 516.11ms | 0.28 / 0.37ms | 2.05 / 2.19ms |
| 十万条混合 | 920.27 / 965.09ms | 55.65 / 69.52ms | 2.50 / 3.03ms |

100、1000、10000、100000条两个样本的完整收件箱请求均为11条实际SQL，其中9条SELECT（含鉴权）、2条事务控制；基础投影为8条批量SELECT。完整状态为17条SQL，当前目标详情为61或63条，后两项没有被计入收件箱的15条上限。详情仅处理准确目标，在这组每会话10条的样本中不随其它会话数量增长。

一万条两个目标均达到。稀疏收件箱相较历史中位数约降低94.7%；它不是完整回复链加速比例。十万条混合收件箱每组20次测量前后RSS增加约424.5MiB，堆增加约272.8MiB；本批没有把大库投影内存成本消除，也不把这些差值解释为峰值或泄漏证明。

一万条的目标分别为收件箱中位数≤150ms、能力回退状态中位数≤50ms。十万条单列容量结果，不套用一万条目标；本批仍按相关事件量构建临时投影，没有引入持久会话投影或全局缓存。

堆/RSS是每组20次读取前后的样本差值，受GC影响，可以为负；它们不是峰值内存，也不表示浏览器内存变化。局部查询、基础空闲轮询的收益不能外推为完整自动回复加速或费用下降。

## 验证与实际运行边界

查询、迁移、刷新、收取、AI统计、预算、清理均使用本地合成回归；真实双通道旧发送链不因本批重新外发。原生新增诊断命令已纳入IPC allowlist并做 Rust 编译检查。源码 `tsx` 与构建后的 Node 冒烟分别记录；桌面Web构建不是安装包验收。

已通过现有开发入口加载业务与原生代码，旧进程正常退出，新后端连接原运行目录。真实库的六索引、备份、完整性及外键已核对，两个版本号保持3。切换前消息前缀逐行摘要不变，切换期间新增入站保留；草稿、意图、收据、预算、授权预占及模型账本摘要不变。新浏览器保持一个专属持有者、无头、静音。此项属于后台实机核对，未把它当作GUI可见效果或真实回复质量验收。

最终整套单元与集成为80文件682项通过；构建后Node的7条冒烟链通过，另运行源码tsx的观察、收件箱同步与自动化冒烟。类型、Web构建、Rust `cargo check --locked`、隐私和800物理行检查通过。

浏览器完整回归覆盖51文件632项：630通过，另外2项分别在修复前加载了自动开关反馈旧实现、以及诊断费用断言仍禁止“未知”文案。开关已以确定延迟红绿修复，相关7文件33项通过，原失败连续20次通过；诊断改为断言“费用：未知”且禁止数值费用和货币符号。最终重新执行诊断、完整会话与刷新3文件22项全部通过。整套结果与修复后定向结果分别记录，不将旧的整套运行称为全绿。所有测试访问本地合成页面，真实模型和真实发送均为零。

合成界面通过不等于已在真实客户端观察新消息或输入。当前最小人工差异检查：

1. 在已连接的开发客户端停留收件箱，等待自然新增消息，确认无需手动刷新便出现。
2. 打开现有会话，输入一段人稿；等待后台变化或切出再回到窗口，确认输入保留。
3. 从左侧收件箱下方进入“AI 与设置”，查看“运行诊断”的模型、通道与证据统计。

提示词质量只观察既有策略内接下来最多4条自然发生的回复，记录是否答到问题、事实、额外承诺和人工修改量。不为评测额外调用或发送；尚无同题对照，不能宣称质量提高百分比或节省费用。

## 维护和回退

首次加载缺失索引时，在调度启动前自动备份至运行目录 `backups/query-indexes-<UUID>.sqlite`，完成副本试安装与摘要核验后，在原库事务中安装。已安装时不重复备份或扫描全库。回退应用代码时保留索引及上线后新数据，不恢复旧整库。

桌面维护仅在后台空闲时扫描证据目录顶层元数据，每批最多100份；模型、采集、发送等业务工作会取消维护。取消后下一次空闲可继续，完成后才延期24小时。被持久引用、未知、链接或无法证明引用完整的文件继续保留。数据库、Profile、私人原始资料、媒体预览不纳入这项元数据清理；原图片预览保留上限不变。释放字节可以为零。

供维护者使用的只读命令为 `pnpm inbora diagnostics --runtime <已有运行目录>`、`pnpm inbora prune-evidence --dry-run --runtime <已有运行目录>`；执行维护为去掉 `--dry-run`，与桌面使用相同保护规则。CLI仍遵循目录锁，不与运行中的持有者并用。
