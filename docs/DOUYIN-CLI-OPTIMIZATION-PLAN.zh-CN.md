**二、上游的架构与本应用的区别**

上游主要路径是 CLI → HTTP/WS Bridge → Tampermonkey → 页面 fetch/IM 协议 → SQLite 辅助索引。它直接请求结构化数据，减少对可见评论行的依赖；ReplyEngine 将模板、人格、作品上下文和成功语料拆开，便于独立调用。

本应用主要路径是 React → Tauri 本机管道 → 共享 Node 服务/SQLite → 账号队列 → 两个专属 Page。读取包含正常页面响应和准确可见 DOM 的绑定；发送还包含版本、持久意图、唯一提交、回读与未知补证。两者产品目标有重叠，但上游没有本应用完整的账本与恢复合同。

本轮不引入新的服务、运行时、第三方账号或 API Key。继续使用现有 DeepSeek 配置；AI 优化的离线验证使用固定响应。真实模型与发送沿用 GUI 已保存的准确策略和剩余额度。

**三、上游确有优化空间，以下缺陷先修才能复用相应路径**

| 问题 | 固定源码 | 核对结果及影响 |
| --- | --- | --- |
| 写操作可能跨传输重投 | `lib/server/router.js:320–364` | WS 任务超时会继续投入 HTTP 轮询；没有按操作类型禁止写重投。合成桩已复现同一表达式先经 WS、后经 poll 两次派发。当前油猴默认走 HTTP，因此此结果证明支持的 WS 路径有缺陷，不说明默认 HTTP 每次都会重复。 |
| WS 身份与结果缺少认证绑定 | `lib/server/ws-hub.js:36–112`、`lib/shared/protocol.js:61–107` | WS 握手未检查 HTTP token/origin；hello 的账号由客户端声明，result 按消息 ID 关联。不可原样作为本应用可信控制通道。 |
| 登出后可保留旧账号缓存 | `scripts/douyin.user.js:63–93` | 强制探测拿不到 uid 时，`if(uid)` 不清旧 account；合成执行返回旧账号。发送检查还可能使用缓存。若移植账号探测，必须以新鲜权威身份替代旧缓存。 |

| 增量混排提前终止 | `lib/commands/get.js:161–166` | 第 1 页同时有新/旧评论便 break，即使 `has_more=true` 且第 2 页仍有新评论。原样 VM 执行已复现。原根较旧也不能据此断言没有新子回复。 |
| 已发送判据较弱 | `lib/commands/post.js:76–95`、`lib/commands/dm.js:49–70` | 发布回包存在 comment、或私信 status_code 非错误便返回成功，缺少现有持久意图与刷新同原生 ID 回读。不能直接用它覆盖本应用送达结论。 |
| 私信未启用写身份门禁 | `lib/commands/dm.js:38,51–53`、`cli.js:266–274` | DM调用未传 `opType:'write'`，loggedCall默认read，因此服务端/页面的expectAccount二次核验未启用。若采用其私信组织，必须修正分类并接现有发送前身份核对。 |
| 本机 Bridge 暴露面较大 | `router.js:160–166,176–182,216–232`、`douyin.user.js:22–26,225–227` | origin 用 startsWith；status 公开返回账号/页面元数据；脚本提交了静态 Bridge token，并支持任意 expression eval。移植相关代码前改成准确 origin、鉴权、固定命令参数及固定原因码，不复制令牌值或原始响应日志。 |
| 存储失败静默、迁移备份失败仍继续 | `lib/memory/comments.js:39–70`、`lib/memory/db.js:296–314` | 返回空/false 会把数据库故障表现为无数据。辅助索引的降级设计不能用在本应用的意图/预算/续查账本上。 |

上游还存在模型价格硬编码、模糊模型名匹配及原始错误片段入日志等问题。它们需要适配，不能借“项目已有实现”跳过验证。

**四、本应用已量化的瓶颈**

`src/storage/store.ts:175–176` 先查询所有 ID，再逐条 SELECT/解析；`inbox-queries.ts:85–110` 全库分组排序后才取 20 行。状态能力回退、同目标历史和自动任务挑选也会触发全量读取，分别位于 `workbench-queries.ts:94–99`、`store.ts:432–439`、`service.ts:659–660`。

纯合成库、Node `v26.13.0`、每个会话 10 条入站、无草稿/收据；预热后取 5 次中位数：

| 事件 / 会话 | getInbox | SQL prepare 次数 | getStatus | SQL prepare 次数 |
| ---: | ---: | ---: | ---: | ---: |
| 100 / 10 | 13.10 ms | 893 | 2.71 ms | 217 |
| 1,000 / 100 | 97.75 ms | 6,503 | 24.76 ms | 2,017 |
| 10,000 / 1,000 | 733.47 ms | 59,603 | 247.10 ms | 20,017 |

prepare 次数是 SQL 编译调用数，不是磁盘 I/O。getStatus 测量的是没有 SEND_AVAILABLE、触发逐事件资格回退的条件；可发通道会短路该分支。此结果证明查询增长成本，不能当成真实账号耗时或平台收取延迟。

EXPLAIN 显示 `send_intents(target_key,status)`、`audit_events(event_type,entity_id)` 当前扫描表；inbound 目标准确查询只用现有唯一索引的账号/通道前缀。仅加索引不能消除上层全库加载。

**六、为何不直接换成上游 fetch/私信协议**

上游 `douyin.user.js:1083–1102` 的评论/回复/本人作品直接 fetch 确实可能省掉大量滚动，这是最值得保留的进一步候选。直接复用源码已经获准；但“改成主动接口收取”会改变当前只接受正常页面请求及可见正文交叉绑定的读取合同，`sendDM/publish` 还改变现有单次 DOM 提交合同。推荐本轮采用第3批的自然响应索引，继续保留直接 fetch 为单独路线决策，不能以复用规则的修改默默替换这些业务合同。

该候选最脆弱的假设是：同源 fetch 在当前专属 Profile 和无头模式中，持续返回完整、正确排序且能准确绑定本人/作品的数据。源码自述和合成测试不证明此假设；若它不成立，页面收取仍必须可用，不能把空响应当成空收件箱。若以后选此路线，应单独批准读取合同变化，先以已授权只读范围做影子对照，证明ID/正文/时间/父子分页等价后再替换读取；发送继续使用唯一协调器。该路线不纳入本次已决定的实施批次。

上游多账号轮换、任意搜索/推广、浏览点赞、图片上传、下载/ffmpeg、多 Provider 和7人格自动轮换均不是当前单账号收件箱优化的必要依赖；本期不加入。直接复制可复用代码与控制产品范围可以同时满足。

**七、验收和交付**

- 查询：旧/新投影对照覆盖两个通道、根/子评论、同文不同ID、旧未知后有新回复、晚到记录、人稿恢复、分页边界和总数；不得通过删数据达到性能目标。
- 调度：40会话、多个坏对象、持续增长会话与新增作品混合，检查两轮公平让出、独立成功水位、超时不写成功、重启不丢续查及急停取消。不得以提高发送并发解决延迟。
- 源码与构建：运行 `pnpm typecheck`、相关 Vitest、`pnpm check:source-size`、`pnpm check:privacy`。读取器/页面序列化变化追加源码 `tsx` 和构建 Node 冒烟；完成批次运行现有相关集成/浏览器闭环，不机械重复整轮发布。
- 相关现有测试：`conversation-inbox.test.ts`、`workbench.test.ts`、`automation-service.test.ts`、`collection-scheduler.test.ts`、`dm-activity-fairness.test.ts`、`deepseek.test.ts`、`evidence.test.ts` 及受影响的读取 e2e。
- 开发继续使用现有 Tauri/Vite；后台变化按需安全重启并先保护草稿、持有者和在途意图。无需每批升版本/安装包。正式包验证在稳定后集中执行。
- 真实人工差异检查仅两项：用户在已打开应用中确认“新入站自动出现且当前人稿不丢”；AI片段变化使用GUI已有授权范围核对少量回复质量。纯查询/通知变化不要求重走旧双通道发送链；真实缺口按实际改动单列。
- 任何复制代码注明固定SHA和修改点，保留MIT文本；测试通过后再登记本地通过范围。当前没有上游整套测试、真实新路线或优化后基准通过结论。

**八、2026-11-10 新增：有头会话查看的打开速度（后续优化）**

用户已实际确认“查看这条消息”能打开正确会话，并明确会话级打开足够，不要求定位到具体一条。用户反馈打开偏慢；本轮仅登记后续优化，不新增性能验收门槛，不将该反馈写成已有毫秒基准或定位失败。
